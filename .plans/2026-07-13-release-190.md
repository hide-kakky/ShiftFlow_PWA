# ShiftFlow 1.9.0 本番デプロイ

## 現在のタスク

- 現在のローカルUI差分を`APP_VERSION=1.9.0`として検証し、Cloudflare Pagesのproduction branchへ直接デプロイする。

## 目的

- スマホ向けヘッダー／メニュー／一覧性改善を、Service Workerの確実な更新単位とともに本番反映する。

## 成功条件

- `frontend/public/app-config.js`、`frontend/public/sw.js`、READMEのバージョンが`1.9.0`で一致する。
- release blockerがなく、静的検査、既存テスト、Pages Functions build、秘匿情報scanが成功する。
- 認証済みCloudflare accountでproduction deploymentが成功し、live HTML／app-config／Service Workerが1.9.0を返す。
- 公開後に主要静的画面、session未認証応答、セキュリティヘッダー、asset配信をread-only smoke testする。

## 再利用した知識

- `cloudflare-deploy`: Pages direct uploadでは認証確認、project／branch明示、deploy後のdeployment確認が必要。
- `nonfunctional-release-guardrails`: production-facing releaseとしてbrowser、Pages Functions、D1、KV、R2、OAuth、logsの境界を確認し、新しいauth／DB／secret変更がないことを分離する。
- `codegraph-local-code-intelligence`: CodeGraph 0.9.9の22 JavaScript files indexを使い、version symbolと影響候補を確認。inline HTMLとproduction proofは`rg`、直接読解、tests、live responseを正本にする。
- repoのService Worker運用: frontend変更時は`app-config.js`／`sw.js`を同一versionへ更新する。

## Scope

- `frontend/public/app-config.js`、`frontend/public/sw.js`、READMEの1.9.0同期。
- 現在の`frontend/public`と既存Pages Functionsをproduction branchへdirect upload。
- predeploy checks、Cloudflare認証／project確認、live read-only smoke test、Plan固定保存。

## 非スコープ

- D1 migration、KV／R2データ変更、secret／環境変数変更、OAuth設定変更、backup Worker deploy。
- Git commit、push、merge、branch変更、既存ユーザー差分の整理。

## 実行計画

1. dirty worktreeとdeploy対象を棚卸しし、Cloudflare auth／project／直前production deploymentを確認する。
2. versionを1.9.0へ更新し、release guardrailとrepo checkを通す。
3. Pages production branchへdirect uploadし、deployment metadataとlive endpointを確認する。
4. release結果、未検証境界、rollback targetを記録し、sanitized Planをarchiveする。

## 検証方法

- Static: version同期、inline script構文、duplicate ID、`git diff --check`、predeploy secret scan。
- Regression: `npm run check`（unit tests、predeploy scan、Pages Functions build）。
- Cloudflare: `wrangler whoami`、project/deployment一覧、direct uploadの成功出力。
- Production read-only: root、app-config、sw、manifest、`/auth/session`、security/cache headers。書き込み系APIと実ユーザー操作は行わない。
- 未検証: iOS／Android実機、認証済み実ユーザー操作、D1／KV／R2 write、通知／メール、長時間monitoring。

## 戻し方

- deploy前はversion差分だけを逆パッチする。deploy後は直前のverified production deploymentをPages rollback機能で再昇格し、live smoke testを再実行する。

## 許可境界

- ユーザーの明示依頼によりversion 1.9.0への変更とCloudflare production deploy、read-only検証まで許可されている。
- commit／push、DB／KV／R2書き込み、secret変更、migration、外部通知は許可範囲外。

## Git / 作業ツリー境界

- current branchには今回までのUI変更とPlan filesが未コミットで存在する。direct uploadはGit commitではなくworking treeの`frontend/public`とrepoの`functions`を反映する。
- `.DS_Store`と`AGENTS.md`の既存差分、Plan filesはdeploy outputへ含めない。commit／pushは実施しない。

## Test matrix

- static／unit／Functions build／secret scan: deploy前に実行。
- production smoke: deploy後にread-only HTTPで実測。
- live data write／real auth／device acceptance: 未実施として分離。

## High-risk boundary

- 分類: production-facing feature release。
- trust boundary: browser ↔ Pages static assets／Functions ↔ OAuth／KV session ↔ D1 tenant data ↔ R2 attachments ↔ diagnostic logs。
- このreleaseでauth、authorization、DB schema、bindings、secrets、upload limit、external API behaviorは変更しない。release blockerは既存testsとlive safe-responseで確認する。

## Rizo接続

- 接続分類: `evidence_asset`
- 再利用した知識: production releaseではUI proofとrelease safety／rollback proofを分離する。
- 増える資産: ShiftFlowのスマホUI改善を本番まで閉じた実績素材と再発防止記録。
- 接続しないもの: productionの内部ID、secret、ユーザーデータをRizo資産へ転記しない。
- 反省と改善: direct upload前後のversion／live response／rollback targetを同じrelease証跡で閉じる。
