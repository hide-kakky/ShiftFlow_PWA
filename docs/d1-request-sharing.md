# D1初手①: 同一操作のHome・一覧再取得を共有

対象候補はAPP_VERSION=2.3.20、基点は2.3.19 / `298556f3a3e89342c3b450701ce1da685fdd0baf`。
これはメッセージ変更後の全件再取得の重複を減らす作業で、DB・スキーマ、APIページ化、永続バッジ集計は変更しない。ステータスバーの実機調査とUI変更は別作業のままとする。

## 発生条件と原因

既存のHome初回応答には、専用メッセージ一覧と同じ本人・所属の閲覧可能な全件が含まれる。初回背景先読みには既に共有処理があるが、メッセージ表示・既読・一括既読・ピン・投稿・削除などの同一操作で `loadMessages({force:true})` と `loadHome({force:true})` が並んで呼ばれる経路は、別々に全件を取得していた。

単純にforceを既存pendingへ合流させると、更新前に始まった要求を再利用して新しい既読・ピン・投稿状態を落とす。全forceをHome待ちにすると、独立した冷起動や遅いHomeからの画面入場を遅らせる。このため、明確な同一操作に限って共有し、本人・所属snapshot・変更世代の境界を同時に保護する。

## 適用範囲と維持条件

- 同一操作の強制更新は `refreshHomeAndMessages()` から一つの新鮮なHome取得へまとめ、Homeとメッセージ表示で結果を共有する。
- 更新・本人切替・所属/認可snapshot更新の前に始まった応答は、保存・描画・fallbackを新しい世代へ適用しない。
- 取得済みsourceと本人の永続cacheは、通信完了を待たず表示する。永続Home cacheをfreshな全件一覧として扱わない。
- 独立したforeground/force、冷起動、Home失敗やmessages欠落時の専用一覧取得は残す。正当な空配列は完了結果として扱う。
- APIが所属IDを常に返すわけではないため、既存の所属情報に加えてbootstrap/認可snapshotのepochで区切る。新しい認可APIやDB問い合わせは追加せず、各APIの既存認可を維持する。
- 一括既読前の未読確認、明細取得、必要なmutation、タスク、個人ピン、全件検索、コメント順、ホーム未読件数と端末アイコン件数の区別は維持する。

一時epochは通信とページ内sourceの採用境界であり、永続cacheのkeyへ持ち越さない。既知の本人・所属情報が同じなら次回起動のcacheを表示できる。APIに所属IDがない場合、別セッションの同email/roleだけから所属の同一性を完全には判定できない既存制約は残る。この作業を、永続cache全体の所属判定や認可失効処理の修正とは扱わない。

別端末の変更反映や手動の新しいforce更新は、先行した同一世代のpendingと区別する。新しい操作を無理に1回へ減らさず、新しい取得結果を優先する。

## バッジの境界

UI/SWの同時要求は、現行の合成試験ですでにraw API 1回にまとまった。bridge/directのmutationも各1回のbadge refreshで、自然な経路の追加2→1を実証できなかった。今回の削減効果へ計上せず、badgeの製品コード・TTL・結果保持は変えない。

完了後のforceは新しい件数を取得するため必要であり、単なる時間間隔で抑制しない。既存のpending中mutationやpush到着の境界問題は、今回のHome・一覧共有とは分けた未改善事項として記録する。

## 検証と計測の扱い

実際のpin/画面refresh入口を使うテストを先に追加し、基点で重複2取得を再現する。共有結果、応答逆転、旧世代の失敗、本人・所属境界、認可、キャッシュ即時描画、独立foregroundの既存契約を検証する。

ブラウザーは実auth/bootstrap/bridgeの入口を通し、HTTPはローカルの合成応答へ全置換する。既存demoだけではbridgeやmutation invalidationを迂回するため、通信数の合格根拠には使わない。実業務データと本番アカウントでの高負荷再現は行わない。

SQL計測はローカルの合成データだけで、実API経路のSQL実行数と返却行数を比較する。返却行数をD1の課金rows_readや本番使用量と同一視しない。通知の94%はユーザー提供の過去情報で、ライブquota・料金・DBの読み取りは実施しない。

合成fixtureは可視message100、閲覧権限のないprivate20、他組織30、comment300、本人task10、個人pin2。実API入口と既存SQLite D1 shimを使い、外部fetchは失敗するstubへ置換した。

| --- | ---: | ---: | ---: |
| 後段refreshのみ | 2→1 | 10→6 | 0→0 |
| 既読＋refresh | 3→2 | 22→18 | 2→2 |

全ケースの削減対象である後段の全件取得は2→1。refreshのみのSQL返却行は224→122（message返却行200→100）。一括既読の事前未読取得は維持し、総操作全体を2→1とは報告しない。Home/messagesの全フィールド・順序、認可による除外、既読、ピン、Home tasksは同じ結果と確認した。

Miniflare直接D1のsmoke checkは応答待ちで停止したため、D1課金のrows_read/rows_writtenは計測していない。上表のSQL数・返却行数・SQLite変更行を、本番の走査行数・料金削減率へ換算しない。

## 再発防止

同一操作の複数表示を更新する際は、別々のforce取得を足す前に共有できるfreshな全件応答を確認する。共有のkeyは本人・所属snapshot・変更世代を含め、古いpendingや完了結果を新しい操作の代用にしない。UI状態の即時描画と通信のPromiseを分ける。

回帰テストでは、単なる最終表示一致だけでなく、要求回数、旧結果の保存拒否、変更後の新しい要求、失敗時の復帰を同じ操作から確認する。バッジは同一世代を証明できない要求をTTLでまとめない。

## 実行・切戻し

`npm run check` と隔離ブラウザーの合格後、候補だけをローカルコミットに固定する。GitHub mainが基点のままで、正規の認証済み経路が使える場合だけ通常fast-forwardで反映し、自動デプロイ成功と公開静的ファイル・版・GitHubコミットを照合する。

DB・cache形式の移行はない。切戻し時はこの候補だけをrevertし、APP_VERSIONを未使用の新しい版へ進め、同じテスト・ビルドを通して再配布する。導入済みPWAに古い版を再使用せず、本人のデータや認証を消去しない。
